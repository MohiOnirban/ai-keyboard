# Phase 2 typing research

## Decoder and data choices

Google's published tap decoder combines a touch model with a weighted finite-state transducer and word n-grams. The literature distinguishes a displayed alternative from an automatic replacement, which calls for a score margin over the literal. KothaKey applies that same distinction with a small native ranker, bounded spelling candidates and explicit confidence rules. It uses adjacency in the Latin key map as a typo signal. It has no calibrated touch-coordinate model or swipe decoder. [Google Research overview](https://research.google/blog/the-machine-intelligence-behind-gboard/) · [Mobile Keyboard Input Decoding with Finite-State Transducers](https://arxiv.org/abs/1704.03987)

AOSP LatinIME includes a native dictionary decoder and Android IME integration. HeliBoard is a GPL-3.0 Android keyboard derived from OpenBoard and illustrates distribution of offline dictionaries. Porting a native dictionary stack would add native build integration on both platforms and require auditing each dictionary separately. Both KothaKey platforms already had a small native implementation, so sharing the frequency and context resources keeps platform integration and upgrade costs smaller. [AOSP LatinIME](https://android.googlesource.com/platform/packages/inputmethods/LatinIME/) · [HeliBoard source and license](https://github.com/HeliBorg/HeliBoard)

The shipped ranker uses an adapted FrequencyWords asset containing 10,000 English and 6,000 Bangla tokens. CC BY-SA 4.0 applies to the adapted list and the full notice ships beside it. The list derives from subtitles and supplies approximate lexical frequencies. It includes some transcription noise, carries no per-token regional labels and cannot justify automatic edits by itself. A separate KothaKey-authored corpus supplies contexts, apostrophes and informal Banglish examples. Avro remains the source of phonetic conversion. [Pinned FrequencyWords source](https://github.com/hermitdave/FrequencyWords/tree/525f9b560de45753a5ea01069454e72e9aa541c6/content/2018) · [Attribution and adaptation](../shared/wordfreq-NOTICE.txt) · [Avro notices](../shared/avro/NOTICE.txt)

## Voice

On Android, KothaKey can switch to an enabled voice input method and subtype. The recognizer chosen by the user controls its languages, on-device availability, microphone consent and treatment of mixed-language dictation. An advertised Bangla or English subtype is evidence of availability in that environment. It does not establish mixed speech accuracy. [Android InputMethodService API](https://developer.android.com/reference/android/inputmethodservice/InputMethodService) · [Android InputMethodSubtype API](https://developer.android.com/reference/android/view/inputmethod/InputMethodSubtype)

On iOS, keyboard extensions do not get microphone access. KothaKey exposes a system keyboard handoff for Apple Dictation. Language coverage, offline operation and code-switching depend on device settings and the available Apple Dictation languages. Apple’s iOS 27 feature list includes English Dictation and omits Bangla Dictation. Bangla keyboard availability is a separate feature. A simulator handoff check verifies navigation only. [Apple custom keyboard extension guide](https://developer.apple.com/library/archive/documentation/General/Conceptual/ExtensibilityPG/CustomKeyboard.html) · [Apple Dictation guide](https://support.apple.com/guide/iphone/dictate-text-iph2c0651d2/ios) · [Apple Dictation languages](https://www.apple.com/ios/feature-availability/#dictation)
